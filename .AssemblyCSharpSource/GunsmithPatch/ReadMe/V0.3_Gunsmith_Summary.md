# Gunsmith V0.3 Summary

## Goal

V0.3 focuses on local persistence for the Gunsmith prototype.

The target is simple:

- `deep_m4` remembers its installed Gunsmith parts
- saved state follows the individual item through Barotrauma save data
- `InventorySprite` and `WorldSprite` restore after loading
- V0.2 nested UI behavior remains unchanged

V0.3 still does not add multiplayer authoritative sync, real physical part items, stat effects, final image previews, or support for a second weapon.

## Result

V0.3 has been tested in game and is currently working well.

Confirmed working:

- Gunsmith UI still opens with `G`
- nested V0.2 UI navigation still works
- installing and removing parts updates runtime sprites
- installed state is written after successful part changes
- reopening the UI shows the current installed state
- saved state is stored on the individual weapon item through `GunsmithData`

## Persistence Design

V0.3 does not write a standalone mod config file.

Instead, each Gunsmith weapon owns its saved state through a lightweight C# item component:

- component: `GunsmithData`
- saved field: `SavedState`
- storage type: string
- save behavior: `[Serialize("", IsPropertySaveable.Yes)]`

`deep_m4` now includes:

```xml
<GunsmithData />
```

This means different save files and different weapon instances do not share one global Gunsmith file. Each weapon item stores its own state inside the normal Barotrauma save data.

## Saved State Format

Lua owns the Gunsmith state format.

C# only stores and returns the raw string.

Saved state uses a small JSON string:

```json
{"v":1,"parts":{"handguard":"m4_handguard_alt","handguard/top_rail":"m4_rail_short"}}
```

Only non-default selections are saved. Default root parts are restored from `Config.lua`, which keeps old saved weapons more flexible when default platform config changes later.

On load, Lua:

- starts from platform defaults
- applies saved non-default selections
- applies parent paths before child paths
- removes invalid paths or missing parts
- rebuilds the existing layer spec for C# sprite composition

## Hook Changes

Existing V0.2 hooks remain:

- `DeepGunsmithApply`
- `DeepGunsmithOpen`
- `DeepGunsmithSetPart`
- `DeepGunsmithCycle`
- `DeepGunsmithEnterPath`

V0.3 adds:

- `DeepGunsmithRequestState`
- `DeepGunsmithSaveState`
- `DeepGunsmithReceiveState`

Flow:

1. Lua initializes item selection from defaults.
2. Lua requests saved state from C#.
3. C# reads `GunsmithData.SavedState`.
4. C# calls back into Lua with the saved JSON.
5. Lua decodes, validates, prunes, and applies the state.
6. Part changes save immediately through `DeepGunsmithSaveState`.

## Lua File Split

During V0.3 cleanup, the oversized `Main.lua` was split into smaller Gunsmith modules:

- `Main.lua` loads the modules and registers hooks
- `Core.lua` contains shared path, slot, part, and validity helpers
- `Persistence.lua` handles JSON encode/decode and saved state application
- `UiSpec.lua` builds the C# UI text protocol
- `Runtime.lua` owns runtime selection, apply, open, set, cycle, and cleanup logic
- `Hooks.lua` registers LuaCs hooks, key input, periodic apply, and item cleanup

This keeps future work on persistence, UI protocol, and gameplay rules from piling into one file again.

## Test Notes

Recommended validation steps:

- modify `deep_m4` root parts
- install nested parts such as rail and optic placeholders
- close and reopen the UI
- drop and pick up the weapon
- save, exit, and reload the game
- confirm UI installed states and composed sprites are restored
- test two `deep_m4` instances with different setups

## Remaining Scope Boundary

Still out of scope after V0.3:

- multiplayer authoritative state
- server-to-client Gunsmith synchronization
- physical attachment items
- inventory cost / consumption
- stat effects
- compatibility rules beyond slot matching
- final image preview UI
- drag-and-drop installation
- workbench / station entry
- support for additional weapons
