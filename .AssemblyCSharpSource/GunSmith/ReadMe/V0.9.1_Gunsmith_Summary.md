# Gunsmith V0.9.1 Summary

## Goal

V0.9.1 is a cleanup and schema polish pass on top of the V0.9 receiver-led model.

The focus is not a new weapon model, but making the growing Lua config easier to manage and adding support for receiver-integrated rail nodes such as the HK416 top rail.

## Result

Implemented scope:

- `Config.lua` now only loads high-level category entry files.
- Weapon config loading moved behind `Config/Weapons/Weapons.lua`.
- Part config loading moved behind `Config/Parts/Parts.lua`.
- AR structure parts were split by role under `Config/Parts/AR/RootCommon/`.
- Shared rails and sights were split into separate files under `Config/Parts/Shared/`.
- M4 and HK416 weapon definitions now live with weapon-family paths under `Config/Weapons/Rifle/...`.
- HK416 receiver now installs a virtual receiver top rail by default.
- Virtual receiver top rail exposes separate front and rear optic mount paths.
- Runtime now supports non-visual virtual parts as coordinate-only nodes.
- UI and compatibility logic now support `mount.partSlot`, allowing unique saved paths to reuse a shared part slot.

## Config Layout

The top-level config entry is intentionally shallow:

```lua
dofile(configPath .. "/Platforms/AR.lua")
dofile(configPath .. "/Weapons/Weapons.lua")
dofile(configPath .. "/Parts/Parts.lua")
```

Concrete file lists are maintained inside the relevant category entry:

- `Config/Weapons/Weapons.lua`
- `Config/Parts/Parts.lua`

This keeps `Config.lua` from becoming a long nested loading script.

## Virtual Receiver Rail

HK416 has an integrated receiver top rail. V0.9.1 models this as a virtual part:

```lua
parts.AR_receiver_top_rail = {
    slot = "receiver_top_rail",
    provides = { "AR_top_rail" },
    item = { virtual = true },
    mounts = {
        { slot = "rear_optic_mount", partSlot = "optic_mount", accepts = { "small_optic", "medium_optic" } },
        { slot = "front_optic_mount", partSlot = "optic_mount", accepts = { "small_optic", "medium_optic" } }
    }
}
```

The virtual part does not consume inventory and does not draw a sprite. It only expands a receiver mount into child optic mount positions.

## `partSlot`

`mount.slot` remains the unique path segment used for UI, save data, and child selection.

`mount.partSlot` is optional. When present, it tells the UI and compatibility checks which part slot should provide candidate parts.

This lets both of these unique paths install normal `optic_mount` parts:

- `receiver/receiver_top_rail/rear_optic_mount`
- `receiver/receiver_top_rail/front_optic_mount`

Without `partSlot`, both paths would need duplicated optic part definitions.

## Runtime Behavior

Runtime anchor resolution now handles virtual coordinate nodes:

- visual parts use their normal `visual.attachPoint`.
- non-visual virtual parts can still receive a parent mount anchor.
- child mounts on a non-visual virtual part resolve relative to that inherited anchor.

This keeps the visual protocol unchanged while allowing invisible structural nodes in the part tree.

## Validation

Validation now understands `mount.partSlot` for default path slot checks.

It also validates that `partSlot`, when declared, is a non-empty string.

## Known Limits

- V0.9.1 does not add a new weapon or platform.
- The receiver top rail anchors still need in-game visual tuning.
- `RootCommon` is still an old directory name; it now contains receiver-mounted structural parts rather than true root slots.
- Broader auto-discovery of config files is intentionally not added yet. Explicit file lists are easier to audit during schema iteration.
